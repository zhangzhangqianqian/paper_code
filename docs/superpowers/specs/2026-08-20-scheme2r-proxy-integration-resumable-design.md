# Scheme2R—调度代理全量集成的分块与断点续跑设计

**状态：** 待用户审阅的冻结设计。本设计只修复全量集成实验的执行、保存、恢复和汇总方式，不改变预测模型、调度代理、LP 约束或科学评价口径。

## 1. 问题定位

现有全量实验对 2021 年 8,757 个四小时滑动窗口和 5 个 Scheme2R 随机种子执行四路诊断：

| 路径 | 负荷输入 | 调度器 | 科学含义 |
|---|---|---|---|
| A | 真实负荷 | LP | 共同外生条件下的已知负荷参照 |
| B | Scheme2R 预测负荷 | LP | 预测误差的下游影响 |
| C | 真实负荷 | 冻结调度代理 | 代理近似误差 |
| D | Scheme2R 预测负荷 | 冻结调度代理 | 完整预测—调度链路 |

A 和 C 在五个种子之间完全相同，现有缓存已使其只计算一次。即便如此，全量运行仍需：

- A 路径：8,757 次 LP；
- B 路径：8,757 × 5 = 43,785 次 LP；
- 合计：52,542 次 `scipy.optimize.linprog(method="highs")`；
- 约 105,084 次唯一的首时步实际结算；
- 175,140 行逐窗口路径明细；
- 2,977,380 行逐窗口影响分解明细。

当前长时间运行不是死循环或模型失效，而是以下执行设计共同造成：

1. 数万次 LP 被单进程顺序求解；
2. 全部种子完成后才开始汇总和正式输出；
3. 没有窗口级检查点、可见进度和断点续跑；
4. 中断后无法复用已经完成的 LP；
5. 最后一次性构造超过 315 万行 Python 字典，增加内存和写盘压力。

## 2. 目标与非目标

### 2.1 目标

1. 保留全部 8,757 个窗口、5 个种子和 A/B/C/D 定义；
2. 将运行拆成可独立验收的连续窗口块；
3. 支持经过哈希验证的 `--resume`；
4. 每块完成后输出进度、耗时和预计剩余时间；
5. 分块与最终结果均采用原子写入；
6. 以流式方式生成大型明细表；
7. 最终仍生成现有科学契约要求的 12 个正式文件；
8. 长时间正式实验仅提供 PowerShell 命令，由用户手动启动。

### 2.2 非目标

本设计不：

- 重新训练或修改 Scheme2R；
- 重新训练、选择或修改调度代理；
- 修改 LP 求解器、设备约束、容量、价格或碳参数；
- 减少正式样本、种子或路径；
- 用代理替代 A/B 的 LP 参照；
- 修改实际结算规则；
- 使用 2021 测试数据调参；
- 在第一版中引入 Windows 多进程并行；
- 修改 Methodology、Experimental Setup、Results 或论文图表。

## 3. 冻结的科学边界

以下内容必须保持不变：

- Scheme2R-H4 的五个正式预测 artifact；
- 冻结物理可行调度代理的权重、标准化统计量和正式收据；
- 标准 IES benchmark、可再生能源序列、价格和初始 SOC；
- `scipy.optimize.linprog(method="highs")` 及其约束；
- A/B/C/D 四路径、首时步共同真实条件结算和影响分解；
- 任务、预测步、路径和 21 个调度变量的固定顺序；
- PyTorch CPU 线程数 1/1 和已冻结运行时配置。

分块大小只属于执行参数，不能改变任何样本或模型输入。

## 4. 推荐执行架构

### 4.1 固定分块

正式执行固定采用连续的 256 窗口分块：

- 前 34 块各 256 个窗口；
- 最后一块 53 个窗口；
- 合计 35 块；
- 分块边界不重新生成样本，也不改变原四小时窗口。

256 在检查点频率和文件数量之间较为平衡。正式执行契约冻结该数值；命令行不能临时覆盖。

### 4.2 阶段 P0：来源与执行指纹预检

预检核验：

- 科学契约和执行契约哈希；
- 五个预测 artifact 的哈希、形状、时间范围和任务顺序；
- 代理冻结文件、权重、标准化参数和正式收据；
- benchmark、可再生能源、价格和调度参数；
- 直接影响结果的相关源文件哈希；
- 冻结运行时设置。

以上信息组成唯一 `execution_fingerprint`。只有指纹完全相同的分块才能续跑复用。

### 4.3 阶段 P1：共享真实路径 A/C

对每个窗口块只计算一次：

- A：真实负荷 + LP；
- C：真实负荷 + 冻结代理；
- A/C 物理诊断；
- A/C 首时步实际结算。

每块保存调度、诊断、结算、时间戳、调用计数和完整收据。

### 4.4 阶段 P2：逐种子预测路径 B/D

对每个种子和窗口块计算：

- B：该种子的预测负荷 + LP；
- D：该种子的预测负荷 + 冻结代理；
- B/D 物理诊断；
- B/D 首时步实际结算；
- 与对应 A/C 块组合时所需的影响分解数组。

共有 35 个共享块和 35 × 5 = 175 个种子块，合计 210 个可恢复工作单元。

### 4.5 阶段 P3：确定性汇总与正式发布

只有 210 个块全部通过指纹、哈希、时间戳、形状和计数校验后才能汇总。固定顺序为：

1. 种子升序；
2. 路径 A、B、C、D；
3. 原始窗口索引升序；
4. 冻结任务、变量、指标和影响顺序。

大型 CSV 从已验证数组流式写入临时文件，不再一次性构造数百万个 Python 字典。全部正式文件完成哈希校验后，临时发布目录才原子提升为正式输出目录。

## 5. 工作目录与分块收据

工作目录和正式目录分离：

```text
<output-dir>.work/
  run_receipt.json
  progress.json
  shared/chunk_0000/
    payload.npz
    chunk_receipt.json
  seeds/seed_2026/chunk_0000/
    payload.npz
    chunk_receipt.json

<output-dir>/
  仅存放全部验收通过后发布的正式文件
```

每个分块收据至少记录：

- schema version 和 `execution_fingerprint`；
- 共享/种子类型、种子和块编号；
- 窗口起止索引及首尾时间戳；
- 样本数和全部数组形状；
- LP 调用数、代理精确 LP 调用数和 fallback 数；
- payload SHA-256；
- 开始、完成时间、耗时和 `status=complete`。

分块先写入同级临时目录，完整验收后再原子重命名。

## 6. 断点续跑与故障语义

### 6.1 可复用分块

`--resume` 只跳过同时满足以下条件的分块：

- 收据状态为 complete；
- 执行指纹一致；
- 种子、索引、时间戳和形状一致；
- payload 存在且 SHA-256 一致；
- LP/fallback 计数符合路径契约；
- 数值有限且必需诊断通过。

标记完成但内容损坏的分块必须 fail closed，不能静默复用、静默删除或与新结果混合。

### 6.2 用户中断

捕获 `KeyboardInterrupt` 后：

- 保留全部已完成分块；
- 将运行级收据记为 interrupted；
- 记录已完成数、当前块和下一块；
- 以标准中断退出码结束；
- 下次以相同契约、工作目录和 `--resume` 继续。

### 6.3 异常失败

异常写入 failed 收据，但不删除或覆盖已完成分块。恢复时必须重新执行 P0 指纹校验。

## 7. 进度与耗时

每完成一个块，控制台输出一行 JSON，并原子更新 `progress.json`：

```json
{
  "stage": "shared_or_seed",
  "seed": 2026,
  "chunk": 7,
  "completed_units": 43,
  "total_units": 210,
  "elapsed_minutes": 112.4,
  "last_chunk_seconds": 154.2,
  "estimated_remaining_minutes": 438.7
}
```

同时报告：

- 共享块完成数 / 35；
- 种子块完成数 / 175；
- 每个种子完成数 / 35；
- 已执行 LP、代理推理和 fallback 数；
- 当前阶段和下一工作单元。

剩余时间只是工程估计，不进入科学结果。

## 8. 允许的结果等价优化

只有通过新旧实现精确对齐测试后，才允许：

1. **批量首时步结算：** 将只包含确定性代数、上下界和成本计算的逐窗口结算改为 NumPy 批量计算；
2. **数组化和流式汇总：** 从列数组直接生成或流式写入 CSV，避免数百万字典对象；
3. **常量复用：** 将窗口内不变的参数和索引移出 Python 内层循环。

第一版不改变 LP 求解器，不做多进程，不把多个窗口合并成一个大 LP，也不通过抽样减少正式工作量。

## 9. 命令行模式

主运行器新增：

- `--dry-run`：只执行 P0；
- `--smoke-limit N`：仅工程验收，明确标记 formal=false；
- `--resume`：核验工作目录后续跑；
- `--work-dir`：可选，默认 `<output-dir>.work`。

正式命令不提供样本限制、块大小或科学参数覆盖。正式运行由用户在 PowerShell 手动启动。

## 11. 测试与验收

### 11.1 单元测试

- 8,757 个窗口分为 35 块，最后一块为 53；
- 索引无重叠、无遗漏并严格按时间排序；
- 分块指纹、形状、计数和哈希校验；
- 批量结算与原逐样本结算对齐；
- 流式 CSV 的列、行和排序与现有实现一致；
- A/C 只计算一次，B/D 每种子一次；
- C/D 的精确 LP 调用和 fallback 始终为 0。

### 11.2 恢复与故障测试

- 人为中断后 `--resume` 跳过已完成块；
- 篡改 payload 时 fail closed；
- 契约、来源或相关代码哈希改变时拒绝旧块；
- 不完整临时块不被视为完成；
- 汇总中断后不需要重算已完成 LP；
- 非空正式目录仍拒绝覆盖。

### 11.3 新旧等价测试

在同一小型冻结样本上运行现有单体流程和新分块流程，要求：

- 调度、诊断、结算和影响分解数组严格相等或满足冻结容差；
- CSV 行数、列名、行顺序和数值相等；
- JSON 科学字段相等，只允许运行时和新增溯源字段不同；
- LP 正式理论调用总数保持 52,542；
- 8 样本冒烟与已经通过验收的优化冒烟结果对齐。

### 11.4 正式准入顺序

1. 新增单元测试；
2. 新旧等价冒烟；
3. 中断与恢复冒烟；
4. 相关预测、代理、LP 和 gate 回归测试；
5. 全测试集；
6. dry-run 指纹预检；
7. 用户手动执行多块续跑冒烟。

全部通过后，Codex 只提供正式启动、进度查询、安全中断和恢复命令。

## 12. 成功标准

只有以下条件全部成立才可重新进行正式实验：

- 新分块流程与现有单体流程在冒烟数据上科学等价；
- 已完成块可恢复，中断或汇总失败不需要重做已完成 LP；
- 进度与预计剩余时间可查；
- 损坏、过期或来源不一致的块被明确拒绝；
- 正式目录只在所有块和最终文件完成验收后出现；
- 最终输出保留现有科学口径和复算能力；
- 所有专项、相关回归和全套测试通过。
